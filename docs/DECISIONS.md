# DECISIONS — webpokerdealer

记录已定的技术决策与理由。**开工前先读，勿轻易推翻**；要改先在此讨论。

## D1 技术栈：Python + FastAPI + WebSocket + 原生前端

- 多设备实时同步（公牌桌 ↔ 各手机）用 WebSocket 最直接
- 单进程同时提供 HTML / REST / WS，**无前端构建步骤**，Docker 部署最省事
- 与个人既有 uv/Python 习惯一致
- **考虑过的其他选项**：*Node/TS + Socket.IO* —— 需要 npm 构建链，对家庭小工具过重，被否
- **当时未考虑的替代方案**：*Django Channels*（复用已有 Django 经验）· *SSE*（本场景其实只需服务端单向推送）
  —— 当时不知道有此选项（技术盲点），未刻意比较过实时方案。

## D2 状态全在内存，无数据库

- 家庭牌局是瞬时的，容器重启丢局可接受
- 免去 DB 迁移、卷挂载、备份等运维负担
- 房间注册表 `game/rooms.py::rooms` 是进程级单例
- 若未来要持久化历史牌局，再加 SQLite（Django 之外的轻量方案）
- **考虑过的其他选项**：*引入数据库*（如 SQLite）—— 要背 DB 迁移、卷挂载、备份等运维负担；
  家庭牌局是瞬时的，重启丢局可接受
- **当时未考虑的替代方案**：*Redis 作进程外共享状态*（可支持 gunicorn 多 worker）
  —— 当时不知道有此选项（技术盲点），选的是默认方案。
  注意：当前方案隐含**「单进程单 worker」**这个前提，多 worker 部署会静默失效。

## D3 服务端权威 + 按角色过滤视图（核心安全不变量）

- 牌堆/底牌只存服务器；`Table.board_state()` 与 `Table.player_state(id)` 是两个出口
- 公牌桌在**摊牌前看不到任何底牌**；玩家只能看到自己的底牌
- 摊牌时只揭示**未弃牌**玩家
- 任何改动都必须有守护测试（`tests/test_table.py`、`tests/test_web.py`）
- **考虑过的其他选项**：*把牌堆下发给前端、由前端负责隐藏* —— 会直接破坏上面的不变量：
  任何设备都能从自己的页面里读到全部底牌

## D4 洗牌用 `secrets.SystemRandom`

- 操作系统级 CSPRNG，无需第三方库
- 测试可注入 `random.Random(seed)` 得到确定性序列
- 实现真实发牌顺序：从庄家左手起逐张发两轮；翻牌/转牌/河牌前各烧一张
- **考虑过的其他选项**：*引入第三方加密库* —— 标准库 `secrets` 已提供操作系统级 CSPRNG，
  不值得为一个函数多一个依赖

## D5 只发牌，不记录筹码与下注

- 筹码/下注在实体桌上完成，程序只解决"洗牌发牌"这件事
- 避免把娱乐工具做成赌博工具，也避免与实体筹码状态不同步
- 弃牌按钮仅用于"摊牌时不亮牌"
- **考虑过的其他选项**：*记录筹码与下注*（做成完整的扑克应用）—— ① 会把娱乐工具变成赌博工具，
  项目红线不允许；② 与实体筹码状态容易不同步；
  ③ **现实里摆弄筹码的过程本身就是牌局的乐趣与关键环节**，搬到屏幕上反而削弱体验

## D6 公牌桌暂不鉴权（已由 D12 取代）

- 家庭局域网内使用，牌桌号（4 位）+ 房间码即隐式口令
- ~~未来如需要，加主持人 PIN~~ → 已实现，见 **D12**

## D7 玩家身份用随机 token，不设账号密码

- 入座时服务端发 `token`，玩家页存 localStorage，WS 连接时校验
- 容器重启 token 失效 → 前端检测到"身份校验失败"自动回到入座页
- 无需注册/登录，符合"朋友在家玩一次"的场景
- **考虑过的其他选项**：*加账号密码 / 注册登录* —— 与"朋友在家玩一次"的场景不符，徒增使用门槛
- **当时未考虑的替代方案**：*用「房间码 + 昵称」直接认人*（省掉 token 下发 / 校验）
  —— 当时不知道有此选项（技术盲点），未刻意设计身份方案。
  事后评估：现方案更稳（防冒名），**保留不变**。

## D8 烧牌照做

- 真实德州每街前烧一张（`Table.burned`），保持仪式感与真实性
- 只统计数量，不展示
- **考虑过的其他选项**：*不烧牌* —— 省几行代码，但会失去真实德州的仪式感（本决策的动机）

## D9 前端零依赖、零构建

- Jinja2 模板 + 原生 JS（`common.js` / `board.js` / `player.js`）+ 手写 CSS
- 不引入 npm/打包器；QR 用服务端 `qrcode` 生成内联 SVG
- **考虑过的其他选项**：*引入前端构建*（npm + 打包器）—— 对这个规模是过度工程；
  连 QR 都能用服务端 `qrcode` 内联 SVG 解决
- **当时未考虑的替代方案**：*htmx* / *Alpine.js*（同样零构建，但能省掉大量手写 DOM 操作）
  —— 当时不知道有此选项（技术盲点）。

## D10 客户端重连策略

- `common.js::connectWS` 对每次断开**只调度一次重连**（带退避，上限 5s）。
  浏览器在握手失败时会先后抛 `error` 和 `close`，若两者都触发重连会滚成风暴。
- 服务端的错误消息带 `reason` 字段；客户端据此区分**可恢复**与**致命**错误：
  - `table_missing`（服务重启导致内存牌桌清空）/ `bad_token`（token 失效）→ **停止重连**并提示用户重新入座/建桌
  - 其它错误 → 正常重连
- 这是必要的：状态在内存（D2），服务一旦重启所有 token 与牌桌都失效，
  否则客户端会无限重连。
- **考虑过的其他选项**：*不区分错误类型、所有断开都重连* —— 见上：会滚成无限重连风暴

## D12 公牌桌鉴权：主持人 PIN + host_token

- **问题**：拿到牌桌号的人都能打开 `/board/{code}` 控制发牌/摊牌/重置/移人（D6）。
- **不是玩家进房密码**：玩家扫码 + 昵称即可入座，**不需要任何密码**（D7 不变）。
  鉴权只针对**主持人控制面**。
- 创建牌桌时服务端生成：`pin`（4 位数字，给人看/输入）与 `host_token`
  （随机 URL-safe，给设备存）。
- 创建接口把两者都返回给创建者（创建者即主持人）；
  `POST /api/tables/{code}/host` 用正确 `pin` 换 `host_token`（错则 403）。
- 公牌桌 WS `/ws/{code}?role=board&token=...` 必须带合法 `host_token`，
  否则回 `reason=bad_host` 并关闭；客户端收到后提示输 PIN。
- 前端：创建时把 `host_token` 存 `localStorage`（键 `wpd:host:{code}`），
  之后重连不再问 PIN；换设备/清缓存才输一次 PIN。
- **PIN 只下发给公牌桌**：`board_state()` 里带 `pin`（便于换设备时在设置中查看），
  `player_state()` 绝不包含（守护 D3）。
- **考虑过的其他选项**：*给玩家也设进房密码* —— 玩家扫码 + 昵称即可入座，多一道密码只增加摩擦；
  鉴权只针对**主持人控制面**

## D13 摊牌自动比牌（最佳 5/7 张）

- **动机**：省去桌上自己比牌的争论。只判断**牌型/赢家**，不涉及下注、赔率、筹码
  （不违反 D5 与项目红线）。
- 评估器 `game/evaluator.py` 是**纯函数**、服务端运行；牌型用一个可比较的元组
  `(类别, *tiebreakers)` 表示，7 选 5 枚举 C(7,5)=21 取最大，简单可靠。
- 处理 A 当 1 的 **A-2-3-4-5 顺子**；类别从高牌→一对→……→同花顺，`A` 高的同花顺
  显示为**皇家同花顺**。
- **只在摊牌时求值**：`showdown()` 里对**未弃牌**玩家评分，结果写入 `_result`；
  `board_state()` / `player_state()` 只在 `street == showdown` 时带出牌型与赢家，
  守护 D3（摊牌前不泄露任何牌型信息）。
- **平局**：并列最高分全部作为赢家，UI 显示“平局：A、B”。
- **张数不足不比（防御）**：`best_hand` 对不足 5 张返回 None。因为摊牌已要求
  河牌发完，正常摊牌时每人都有 7 张可评，这个分支只在异常情况下生效。
- **考虑过的其他选项**：*让人在桌上自己比牌* —— 正是本决策要消除的争论（见「动机」）；
  *连筹码 / 赔率一起算* —— 违反 D5 与项目红线，不做
- **当时未考虑的替代方案**：*现成的扑克评估库*（如 `treys` / `phevaluator`）
  —— 当时不知道有此选项（技术盲点）；自写 `evaluator.py` **并非**出于「有意避开依赖」。
  事后评估：若重做**会优先选用开源库**，自写仅作为无依赖的备选保留。

## D14 外观自定义：CSS 变量 + localStorage

- 通过 CSS 变量驱动外观：`--felt*`（牌桌背景）、`--card-back*`（牌背）、
  `--suit-*`（牌面花色）；预设写在 `common.js`（`THEMES` / `CARD_BACKS`）。
- **每台设备各自保存**（localStorage），不占用服务端状态，符合“无数据库”的前提。
- 牌面色用 `card--suit-{suit}` 类选择（而非内联颜色），这样切换“四色牌”时
  能即时生效；四色牌通过 `body.deck-four-color` 覆盖 `--suit-*`。
- **图片牌组**：可选地用图片牌面。牌组放在 `static/cards/`，用
  `decks.json` 登记；卡牌用 `背景图` 贴上对应图片（文件名 = 点数+花色，
  如 `As.png`）。没有图片时自动用内置 CSS 牌面。切换牌组时页面通过
  `appearancechange` 事件重绘（图片是烙在元素上的）。
- **版权**：只支持公有领域/CC0/允许再分发的牌组；README 已注明。
- **内置一套**：`static/cards/knoll/` 收录了 Byron Knoll 的矢量扑克牌（公有领域，
  SVG，放大不糊）；在 `decks.json` 登记为 `knoll`。该套无牌背，用内置 CSS 牌背。
- **考虑过的其他选项**：*把外观偏好存到服务端* —— 会占用服务端状态，违背 D2「无数据库」的前提；
  *允许任意牌组图片* —— 有版权风险，故只收公有领域 / CC0 / 允许再分发的牌组

## D11 发牌与“下一局”解耦，摊牌是独立动作

- **发牌推进不自动到摊牌**：`next_street()` 只走到河牌，河牌后必须显式
  `showdown()`。现实中只有在河牌且无人弃牌时才需要摊牌，多数牌局在下注阶段
  就结束了，摊牌用不上。
- **摊牌只在河牌发完后可用**：`showdown()` 要求 `street == RIVER`，否则报错
  （翻牌前后点摊牌会被拒绝）。提前结束的局用「开始下一局」结算，不走摊牌。
- **`start_hand()` 可在任意街道调用**：一局可能提前结束（大家都弃牌，或者
  主持人直接开下一局）。“开始下一局”与发牌互不依赖，不必先把五张公共牌发完。
- **未摊牌的牌局不记录底牌**：`_finish_hand()` 只在摊牌时写下未弃牌玩家的底牌，
  提前结束的牌局只记录公共信息（谁弃牌、发了哪些公共牌）。历史日志是公开数据，
  不得泄露任何未亮出的底牌（守护 D3）。
- **摊牌只记录一次**：`_hand_recorded` 防止“摊牌后再开新局”把同一局记两遍。
- **中途入座**：新玩家可随时入座，但只从下一局开始发牌（本局不下发底牌）。
- **座位顺序可调**：`move_player()` 交换相邻座位来反映实际就座方向，
  因为座位顺序决定按钮轮转、盲注与发牌顺序。
- **庄家位可手动纠正**：`set_dealer()` 把按钮放到指定玩家；牌局进行中会同步重算
  本局大小盲，未开局/已结束时则标记为“下一局的庄家”并跳过自动轮转。
- 这些改动都有守护测试（`tests/test_table.py`、`tests/test_web.py`）。
- **考虑过的其他选项**：
  - *发牌自动推进到摊牌* —— 现实中多数牌局在下注阶段就结束了，摊牌多半用不上。
  - *任意街道都能摊牌*（早期实现如此）—— 会把「提前结束」与「亮牌比较」两件事混在一起，
    已改为只在河牌发完后可用。

## D15 部署形态：局域网常开宿主 + 多架构镜像

- 本 app 是“局域网 + 长连接 + 内存态”，只需**一场牌局期间服务常开**；
  **不引入公网 / 云 / HTTPS**（同网段即可，手机需与宿主同一局域网）。
- 宿主可选：**NAS**（家里长期）/ **树莓派**（随身便携）/ PC（临时）。
  客户端（手机、平板、**iPad**）只浏览器访问；**iPad 不能跑 Docker**。
- 镜像发布为**多架构**（`linux/amd64` + `linux/arm64` + `linux/arm/v7`），
  NAS 与树莓派都能直接 `docker pull`；推送用 Docker Hub 或 GHCR，
  **凭据只在本机，不入库**。
- 树莓派便携注意：用 mDNS（`<主机名>.local`）找地址（Android 解析不总可靠→靠二维码）；
  留意访客 Wi‑Fi 的**客户端隔离**（可让 Pi 开热点或带旅行路由器）；外出需供电。
- 详细步骤与对比表见 `docs/DEPLOY.md`。
- **考虑过的其他选项**：*公网 / 云 / HTTPS 部署* —— 本 app 是「局域网 + 长连接 + 内存态」，
  只需一场牌局期间服务常开；引入公网会带来证书、暴露面与额外运维成本
- **当时未考虑的替代方案**：*Tailscale* / *Cloudflare Tunnel* 等零配置组网
  —— 当时不知道有此选项（技术盲点），未比较过「必须同一局域网」以外的方案。
  对「树莓派便携 + 外出」场景可能特别有用。
